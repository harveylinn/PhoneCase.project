# 會員系統：單表規格與團隊串接約定

版本：2026-10-30｜第三組手機殼銷售專題｜
## 1. 本次決定與適用範圍

會員資料統一集中於 `members`，地址與更新時間同表保存，第一版不使用 `memberprofiles`。

技術背景：React＋TypeScript、Spring Boot、MySQL。本站登入採 JWT；一般登入使用獨立帳號 `account`，本次新增 Google 登入所需的資料欄位。

本文件以本次確認的新建表 SQL 為準，統一團隊欄位名稱與串接規則。文件及 SQL 完成，不代表資料庫已套用，也不代表所有功能已實作或驗收。本次未重新檢查 GitHub 程式，API 的現況仍須與實際程式核對。

Google 登入相關流程列為本次待實作規格；首次建立帳號、綁定與密碼設定策略見第 5 節。

## 2. 欄位規格

以下為資料庫欄位名稱。Java 屬性及 API JSON 可以採 camelCase，但需由會員負責人公布對應，不要求 JSON 直接沿用資料庫底線命名。

| 欄位 | MySQL 型別 | 限制／預設值 | 用途 |
|---|---|---|---|
| `id` | `BIGINT` | 主鍵、自動遞增 | 本站會員編號，購物車與訂單以此關聯 |
| `account` | `VARCHAR(100)` | 必填、UNIQUE | 本站帳號；Google 新會員也必須有值 |
| `email` | `VARCHAR(255)` | 必填、UNIQUE | 聯絡信箱，後續可供密碼重設使用 |
| `password_hash` | `VARCHAR(255)` | 可空，預設 `NULL` | BCrypt 密碼雜湊；Google 專用會員可無本站密碼 |
| `google_sub` | `VARCHAR(255)` | 可空、UNIQUE；`ascii_bin` | Google 回傳的 `sub`，識別綁定的 Google 帳號 |
| `name` | `VARCHAR(80)` | 必填 | 會員姓名，不必等同當次訂單收件人 |
| `phone` | `VARCHAR(30)` | 可空，預設 `NULL` | 聯絡電話，以字串保留前導 0 |
| `default_address` | `VARCHAR(500)` | 可空，預設 `NULL` | 單一預設收件地址 |
| `role` | `VARCHAR(20)` | 必填，預設 `CUSTOMER` | `CUSTOMER`／`ADMIN` |
| `status` | `VARCHAR(20)` | 必填，預設 `ACTIVE` | `ACTIVE`／`SUSPENDED`／`DELETED` |
| `created_at` | `DATETIME` | 必填，預設目前時間 | 註冊時間，更新資料時不變 |
| `updated_at` | `DATETIME` | 必填，預設目前時間，更新時刷新 | 最後修改時間 |

命名統一：資料表使用 `members`；一般會員角色使用 `CUSTOMER`；手機、地址、密碼雜湊及時間欄位分別使用 `phone`、`default_address`、`password_hash`、`created_at`、`updated_at`。原文件中的其他名稱不再作為資料庫規格。

必填也必須由後端驗證：`NOT NULL` 不會阻止空字串。長度、格式與錯誤訊息由後端統一，前端驗證用於改善操作體驗。密碼不可自動 trim，以免改變使用者設定的內容。

一般帳密註冊仍須提供密碼；資料庫允許 `password_hash = NULL`，是為了支援 Google 登入，不代表一般註冊可以省略密碼。

## 3. 角色與帳號狀態

角色決定能操作什麼，狀態決定帳號能否使用。

| role | 意義 | 操作範圍 |
|---|---|---|
| `CUSTOMER` | 一般會員 | 自己的會員資料、購物車與訂單 |
| `ADMIN` | 管理員 | 團隊約定的後台管理功能 |

| status | 意義 | 處理規則 |
|---|---|---|
| `ACTIVE` | 正常 | 可登入及使用授權功能 |
| `SUSPENDED` | 停權 | 禁止登入與受保護操作，可解除停權 |
| `DELETED` | 軟刪除 | 保留會員及訂單關聯，禁止登入；會員列表預設排除 |

`DELETED` 是約定的軟刪除值，是否已有對應操作須另行驗收。軟刪除後保留 account、email 與 google_sub 的唯一限制，不允許以相同資料建立另一位會員。軟刪除不等於清除個資。

註冊一律由後端設定 `CUSTOMER`、`ACTIVE`。一般會員不能修改 role、status 或自行指定 google_sub。此 MySQL 5.7 相容版本由後端驗證允許值，不依賴 CHECK 限制。

## 4. 各功能如何使用資料

| 功能 | 輸入／讀取 | 後端處理 |
|---|---|---|
| 一般註冊 | account、原始密碼、email、name；phone 可選 | 驗證及查重；以 BCrypt 雜湊密碼；google_sub 留空；建立 CUSTOMER、ACTIVE |
| 一般登入 | account、原始密碼 | 查帳號；檢查 password_hash 存在，再驗證 BCrypt 與會員狀態；成功後簽發本站 JWT |
| Google 登入（待實作） | Google 提供的身分憑證 | 後端完成憑證驗證，依可信的 sub 查找／建立會員，檢查狀態，簽發本站 JWT |
| 登出 | 前端保存的本站 JWT 及登入資料 | 前端移除 token、清除登入狀態；伺服器撤銷能力見第 6 節 |
| 個人資料查詢 | 後端驗證後的目前會員 | 僅回傳必要資料，不回傳 password_hash 或身分憑證 |
| 個人資料修改 | 姓名、手機、預設地址 | 從登入身分決定更新對象；使用專用 DTO，只更新允許欄位 |
| 修改密碼（需驗收） | 原密碼、新密碼 | 有本站密碼者驗證原密碼後重新雜湊；Google 專用會員另走設定密碼流程 |
| 後台管理（依團隊分工實作） | 查會員、變更角色／狀態 | 後端確認 ADMIN 及 ACTIVE；禁止任意欄位整筆覆寫 |

不要直接回傳或接收整個 Entity。註冊 API 接收原始密碼的欄位名稱，由 DTO 定義；`password_hash` 是資料庫儲存欄位，不是前端應送來的密碼雜湊。

## 5. Google 登入與會員資料規則（待實作）

### 5.1 兩種登入共用一位本站會員

| 會員情況 | password_hash | google_sub |
|---|---|---|
| 只用帳密登入 | 有 BCrypt 雜湊 | NULL |
| 只用 Google 登入 | NULL | 有 Google sub |
| 帳密及 Google 均已綁定 | 有 BCrypt 雜湊 | 有 Google sub |

後端應確保建立會員時至少有一種可用登入方式，不能把兩欄皆為 NULL 的資料當作正常完成註冊。

`google_sub` 不是本站 JWT，也不是 Google access token，不可把 token 存進這個欄位。購物車與訂單仍關聯 `members.id`，不改成關聯 google_sub。

Google 身分資料必須取自後端驗證通過的憑證，不直接相信前端傳來的 email、sub、角色或會員 id。憑證應檢查簽章、有效期限、發行者與目標用戶端等必要條件；實作流程選定後再確認完整驗證項目。

### 5.2 首次 Google 登入的 account

目前 account 仍是必填且唯一，因此不能只寫入 email、name、google_sub。

建議第一版由後端產生不重複的本站 account；此策略尚需在實作時定案。若改採讓使用者自行設定，必須先完成補填與查重才能建立完整會員。不可直接把固定字串或可能重複的姓名當作 account。

### 5.3 與既有 Email 重複

先以 google_sub 查找既有綁定。如果未找到，但 email 已被其他本站會員使用，第一版建議拒絕直接建立或自動綁定，提示先用原方式登入，再走明確的 Google 綁定流程。

不要只因信箱相同就直接將 Google 身分寫入既有會員。綁定功能若尚未實作，先提供清楚的衝突訊息，不顯示尚不可用的操作。

### 5.4 無本站密碼的情況

password_hash 為 NULL 時，一般帳密登入應安全拒絕，不可直接拿 NULL 執行 BCrypt 驗證。Google 專用會員若要增加本站密碼，需要另外的身分確認與設定流程；不能要求一組從未建立過的「原密碼」。

同一 google_sub 後續登入須對應原本的 members.id。停權或軟刪除會員不可透過 Google 登入繞過限制。

## 6. JWT 與登入狀態約定

一般登入與 Google 登入成功後，均使用本站簽發的 JWT 呼叫受保護 API。Google 憑證只供後端確認 Google 身分，不直接取代本站 JWT。

前端依現行專案方式保存 token，受保護請求使用：

```http
Authorization: Bearer <本站 JWT>
```

後端統一驗證 JWT，再取得目前會員。JWT 內識別會員所用的 subject／claim，須沿用會員模組實際設定；不能假設目前 JWT 已改用 id。其他模組應使用驗證完成的會員資料，避免自行解析各種不同 claim。

權限驗證目標：每次受保護請求重新確認會員仍存在，且目前 status 與 role 符合要求。只相信 token 簽發時保存的舊角色，會使停權或降權無法及時生效；是否已達成此規則須驗收。

登出清除前端 token 後，該瀏覽器不再主動帶入 token。但在沒有撤銷清單或其他撤銷機制時，已取得的 JWT 在到期前仍可能被使用。不可宣稱「前端登出等於伺服器立即撤銷 JWT」。變更密碼是否撤銷舊 token 也須另定機制並驗收。

## 7. 組員串接約定

| 負責功能 | 需配合事項 |
|---|---|
| 會員（哲宇） | 提供登入結果、目前會員資訊、統一驗證方式及 API JSON 格式 |
| 商品（志強） | 公開商品瀏覽可不登入；需要身分時沿用團隊登入導流規則 |
| 購物車（秉豪） | 後端從驗證完成的會員取得 id，不直接相信前端傳入的會員 id |
| 訂單（奕瑋） | 關聯 members.id；建立訂單時另存當次收件資料；查詢時驗證訂單歸屬 |
| 後台（佑政） | 後端檢查 ADMIN 與 ACTIVE；隱藏前端按鈕不能代替權限驗證 |

受保護 API 的回應約定：未帶 token、token 無效或過期回應 401；已確認身分但角色不足，或會員狀態不允許操作，回應 403。登入 API 的錯誤訊息與狀態碼須另外統一，不能混同所有情況。

前端遇到 401 可依情境引導重新登入；403 顯示無權限或帳號狀態訊息，不要將所有錯誤都導向登入頁。

依既有專案約定，會員 API 前綴為 `/api/member`，資料表為 `members`，兩者用途不同。既有約定包含 POST `/register`、POST `/login`、GET `/me`、GET `/exists`；此處不據此宣稱目前分支所有介面均已驗收。Google 登入 API 的網址、請求格式及回應 DTO 在實作時由會員負責人公布。

未登入從購物車或結帳導向登入頁時，前端保留原站內目標。一般登入與 Google 登入成功均沿用相同返回規則；只接受允許的站內路徑，無有效目標則回首頁。登入及註冊不應清空購物車。

## 8. 預設地址與訂單地址

`members.default_address` 是下次結帳可預先帶入的地址。姓名、手機、地址可以作為結帳初始值，使用者仍能修改當次收件內容。

訂單必須保存當次收件姓名、電話、地址。例如十月訂單寄台中，十一月會員改成台北，十月訂單仍須顯示台中。不能以會員目前的地址取代歷史訂單地址。

第一版一個預設地址即可，未來需要多組地址時再新增一對多地址表。

## 9. 新建資料表 SQL

以下配合本次提供的 MySQL 5.7.24 建表規格，適用於尚未建立 members 的資料庫，不含測試資料。既有資料表不可直接重複執行 CREATE TABLE，應另用 ALTER TABLE 調整。

```sql
CREATE TABLE `members` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT,
  `account` varchar(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  `email` varchar(255) COLLATE utf8mb4_unicode_ci NOT NULL,
  `password_hash` varchar(255) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `google_sub` varchar(255) CHARACTER SET ascii COLLATE ascii_bin DEFAULT NULL,
  `name` varchar(80) COLLATE utf8mb4_unicode_ci NOT NULL,
  `phone` varchar(30) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `default_address` varchar(500) COLLATE utf8mb4_unicode_ci DEFAULT NULL,
  `role` varchar(20) COLLATE utf8mb4_unicode_ci NOT NULL DEFAULT 'CUSTOMER',
  `status` varchar(20) COLLATE utf8mb4_unicode_ci NOT NULL DEFAULT 'ACTIVE',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_members_account` (`account`),
  UNIQUE KEY `uk_members_email` (`email`),
  UNIQUE KEY `uk_members_google_sub` (`google_sub`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

SHOW COLUMNS FROM `members`;
SHOW INDEX FROM `members`;
```

account、email、google_sub 各有獨立唯一索引，不可改成一個複合唯一索引。google_sub 可以有多筆 NULL，讓尚未綁定 Google 的會員同時存在；不要用空字串代替 NULL。

建立及更新時間由資料庫維護，Java Entity 寫入策略須配合，避免把時間寫成 NULL 或覆寫建立時間。全組統一資料庫連線時區及顯示方式；DATETIME 本身不保存時區資訊。


## 給組員快速看

會員統一放 `members`，購物車與訂單關聯 `members.id`。一般會員角色為 CUSTOMER，管理員為 ADMIN；狀態為 ACTIVE／SUSPENDED／DELETED。account、email、google_sub 各自唯一，google_sub 可為 NULL；Google 專用會員的 password_hash 可為 NULL。

本站以 JWT 驗證登入，一般與 Google 登入共用相同會員身分及串接方式。Google 登入流程仍待實作驗收。會員 id 由後端驗證後取得，不直接相信前端指定值。default_address 只作預設地址，訂單另存當次收件資料。密碼雜湊不回傳前端，一般會員不能修改角色、狀態及 Google 綁定識別值。
